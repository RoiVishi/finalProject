## E1 — 8.11.2026 — Advisor items 1, 4, 5, 8: first checks

**Question.** Does scenario B's AUC 0.85 come from the model recognising projects (item 1)? Do duplicate project families inflate scenario A (item 4)? Does the model behave differently with the inputs the service really sends (item 5)? Does the model beat simple rules (item 8)?

**Run.** `python3 src/advisor_checks.py` → `outputs/advisor_checks.json` (about 1 minute).
- Corpus: `outputs/corpus_v3_buildings.csv` (registry v6 corpus, 66 projects, 9,250 activities).
- Model: XGBoost with the v6 hyper-parameters, fixed in every split (no nested grid search), so all variants are trained identically.
- Scenario A: 20 GroupShuffleSplits, 25% of projects in test. A_project groups by project (as in v6); A_family groups by schedule family.
- Families are generated by code from identical project signatures: 66 projects → 59 families. Merged: DSLIB C2016-18/19/20, C2016-21..24, C2016-25/26, and 129 trial with 130 TRIAL.
- Within-project AUC: projects with ≥30 test activities and ≥5 in each class (23 projects in A, 7 in B).

**Result (within-project AUC is the product metric).**

- clean − planned-duration rule: +0.048 [+0.014, +0.095], better on 16 of 23 projects.

Point 4 does not: the "+0.05, CI above 0" edge of the clean set over the planned-duration rule came from one random-split design and one family map. On fixed family folds and cleaned rows (E2b), the edge is not significant, and the clean set does not beat the number-of-successors rule. Do not quote point 4.

**What this shows.**
1. Item 1 confirmed. The two project features alone reach pooled AUC 0.816 in B and 0.740 in A, with zero ranking inside a project. On a new project (A_project), they score higher pooled than the full model (0.740 vs 0.734). Removing them drops B from 0.874 to 0.793 pooled, and from 0.769 to 0.650 within project. So in B the model also uses them to learn project-specific patterns.
2. Item 4 confirmed for the pooled metric. Grouping families drops the full model's pooled A from 0.734 to 0.640. Within-project AUC does not move (0.560 → 0.566), because the duplicate DSLIB projects are single-class and never enter the within-project metric.
3. Item 5: the train/serve mismatch barely changes ranking or the mean probability. It still has to be removed, because the evaluation must describe the model that runs.
4. Item 8: on a new project, the v6 model is not better than ranking by planned duration. The clean feature set is modestly better (+0.05 within-project AUC, top-10% lift 1.19).

**Caution (item 9).** These are exploratory comparisons on the same 66 projects that earlier decisions were made on. The clean set's advantage is a direction, not a final result. The final number must come from a frozen family-level test set, evaluated once.

**Decision.** Next model iteration: drop proj_span_days, proj_n_tasks, both float columns and task_type; group every split by family; headline = A_family within-project AUC with CI, next to the planned-duration rule. Before training it: clean the rows (item 6) and measure survivorship (item 3). No change to the served model yet.

## E2b — 8.11.2026 — Where E1/E2 departed from the advisor's instructions

**Why.** Two re-reads of the feedback against E1/E2 found eight places where we did something other than what was asked:
1. E2 compared runs on different project sets and families (item 9).
2. Survivorship was not computed per project × decile (item 3).
3. The two label definitions were not compared side by side (item 6).
4. Results were not reported by corpus (item 6).
5. The top-10% measure was a median, not a table per project (item 1f).
6. The family rule ignored containment (item 4: "no containment check on DSLIB").
7. Under the new fixed folds only one of the four requested baselines was run (item 8).
8. BHD "planned" dates were not compared between versions of the same project (item 2).

**Run.** Rebuild the families with containment, then run the follow-ups:
```
python3 src/e2_data_audit.py
python3 src/e2b_followups.py
```
Outputs: `project_families.json` from the first; `e2b_followups.json` and `e2b_label_disagreements_sample.csv` from the second. Needs `data_bhd`; about 2 minutes. E2's family map (Jaccard only) is kept as `outputs/project_families_jaccard_only.json`. To reproduce E2, pass that file to `--families`.

**Family rule, corrected.** Pairs of projects are linked when Jaccard ≥ 0.5 OR containment ≥ 0.8 with ≥ 5 shared names. 66 projects form 44 families (46 with Jaccard only). The change joins C2016-14 and C2016-15 (all 13 names of C2016-15 appear in C2016-14) to the C2016-11/12/13 family. Limitation: names are mostly Spanish/Dutch in DSLIB and English in BHD, so name matching can hardly find a family that spans both corpora. "No cross-corpus families" is therefore a weak negative, not a finding. (Egyptian and Belgian schedules sharing a template is unlikely, but this check does not show it.)

**Design change: fixed folds.** A first version used 20 random GroupShuffleSplits per run. The splits depend on the set of groups, so dropping two projects re-drew every split, and the split-to-split noise was as large as the effects being compared. The comparison now uses one plan of family → fold assignments, 10 × 5-fold, computed once from the 66-project family map and reused in every run. Each project is tested 10 times with the same companions. **All future comparisons (E3, E4) should use fixed folds.**

**(3, 8) Label definitions.**
- DSLIB (2,841 activities): grew is 17.5% in working days and 23.5% in calendar days; the two agree on 89.4%. The tolerance label (> 20% and ≥ 2 working days) gives 10.2% and keeps 58% of the positives.
- BHD (4,844 activities): grew is 63.3% in calendar days and 63.6% in working days. The two agree on 98.9%. The tolerance label gives 52.6% and keeps 83% of the positives.

The task names of 129 trial / 130 TRIAL are mostly blank, so their name-based family link rests on few names.

**(9) The advisor's survivorship hypothesis (item 3).** "Only the fast activities of the late part had finished." The test takes the BHD activities that had started by the data date and compares the planned duration of those that finished with those still running.

- So the labelled late activities are mostly the short ones. This supports the advisor's explanation of the "drift" 0.46 → 0.29.
- In the 60–80% deciles the difference reverses (96 vs 80 hours), but there are few running activities there.

**(8) BHD versions of the same project (item 2).** Two corpus projects have earlier versions in the raw data, with the same task codes, where every activity is not started:
- `update of jungle 20-07-2010` vs `baseline of jungle` (the same P6 project: proj_id 764, same guid): for the 73 completed activities, the planned duration in days and in hours is the same in 100% of cases, but the planned start is the same in only 47%.

  - It was added to the P6 database on 27.6.2010 at 10:16, and every activity has update_date 27.6.2010 10:17. So here update_date records the import, not an edit.
  - The first actual start in the update is 21.6.2010.
- `Update 01-09-2010` vs two earlier drafts, which are one P6 project exported at two moments (proj_id 766, same guid, add_date 29.6.2010). Neither draft has actual dates.
  - `schedule of Medor`: 76 activities, every update_date is 6.7.2010, planned project start 10.7.2010.
  - `medor_003`: 69 activities, every update_date is 23.8.2010, planned project start 7.7.2010. The first actual start in the update is also 7.7.2010.
  - Between the drafts, 7 activities were removed, and 26 of the 69 shared activities have a different planned duration. All 26 are shorter in `medor_003`.
  - The 16 completed activities of the update have the planned duration of `medor_003` in 16 of 16 cases, and that of `schedule of Medor` in 12 of 16 (A1330, A1370, A1390 and A1410 differ).
- *Correction (15.11.2026, from Shira's check).* The first version of this entry said that in both projects the planned durations of the completed activities "are the original ones". That was too strong for jungle and wrong for Medor.

The baseline's data date and its lack of actual dates fit a start-of-project plan, but they do not prove that it is the original plan.
  - Medor: `medor_003` is a plan that was revised about six weeks after work started, and the update takes its planned durations from it.   - Caveat: update_date changes on every edit and on import, so it dates the last change and says nothing about what was changed. The order of the two Medor drafts rests on update_date and on the planned project start moving to the actual start date.
- **Decision (Roi and Shira, 15.11.2026).** Medor stays in the corpus and is flagged, like rehab-2. It has 11 activities in the cleaned corpus (0.2% of the BHD rows) and is too small for the within-project metric. The 90% rule of E2 does not apply to it.

  - Earlier versions exist for only 2 of the 7 BHD projects in the cleaned corpus. In one of them (Medor) the plan was revised after the start. For the other 5 this cannot be checked.
  - rehab-2 is the largest case: 2,035 of the 4,844 BHD activities in the cleaned corpus (42%). Its planned start equals the actual start in 100% of activities (E2), so its label rests on the assumption that the planned durations were kept. There is no earlier version to test that.
  - Jumaira (E2) shows the opposite case, where durations too were overwritten.

## Data check — 15.11.2026 — DSLIB source, version and release notes (item 11)

## D1 — 15.11.2026 — Decisions before the freeze

**Why this entry.** We asked the advisor two questions before freezing a test set: whether the proposed freeze is acceptable, and which label to prefer. Her answer, in translation: with so little data every decision is problematic; she accepts any reasonable decision, on condition that it is documented in the pipeline together with what it means for the results and the limits on their validity. This entry is that documentation. It was written before the draw of the frozen set and before any E3 result.

**Who decided.** Roi and Shira took all the decisions below together, on 15.11.2026.

### 1. Primary label and metric: `grew`, within-project AUC

- Decision: the primary label stays `grew` (actual duration longer than planned), defined per corpus as in E1–E2b. The headline is the within-project AUC: median over the eligible projects, with a bootstrap confidence interval over projects.
- Alternatives considered: the tolerance label as primary; the continuous ratio (actual / planned duration) as primary.
- Numbers (E2c, no model): eligible DSLIB projects 17 with `grew`, 12 with the tolerance label, 20 with the ratio (rule B). Expected eligible projects in a frozen set of 15: 6.0, 4.2 and 7.0.
- Reason: the ratio adds 3 eligible projects, and about one in the frozen set. Against that, it would break the comparison with E1–E2b and need a new quality gate, a new top-10% table and re-scored baselines.
- What it means for the results: `grew` keeps very small overruns. In DSLIB, 26% of the overruns are of one working day or less (E2). So part of what the model is scored on is rounding, not delay. Sensitivity S1 answers this.

### 2. Sensitivity S1: the tolerance label

- Decision: every headline result is also reported with the tolerance label: overrun of more than 20% and at least 2 working days.
- The advisor wrote "more than 20% and at least a number of working days". The number 2 is ours: an overrun of a single day can come from rounding, and 26% of the DSLIB overruns are of one working day or less (E2).
- Reading rule, fixed now: if the comparison between the model and the best baseline gives a different conclusion under `grew` and under S1, both are reported and the document says that the conclusion depends on the label definition.

### 3. Secondary metric: C-index on the continuous ratio

- Decision: next to the AUC we report the concordance index inside each project: of the pairs of activities with different ratios, the share the model ranks in the right order. It is computed from the same model scores; no extra model is trained for it.
- Eligibility for it: ≥ 30 activities and ≥ 125 comparable pairs (rule B of E2c). 20 DSLIB and 5 BHD projects.
- It is reported next to the headline and never replaces it.

### 4. Eligibility for the within-project AUC: unchanged

≥ 30 activities and ≥ 5 in each class. With `grew`: 17 DSLIB and 5 BHD projects (E2c).

### 5. Running activities that already passed their planned duration (item 3): in the main analysis

- Decision: a BHD activity that was still running at the data date, and had by then been running longer than its planned duration, enters the main analysis with `grew` = 1.
- Alternatives considered: leave them out, as in E1–E2b; use them in a sensitivity analysis only.
- Numbers: 1,731 such activities in the 7 BHD projects, of which 1,439 are in CCA (129 trial 104, 130 TRIAL 37, PORTO MATROUH 22, rehab-2 122, jungle 7, Medor 0). BHD goes from 4,844 to 6,575 activities and its `grew` rate from 63.3% to 72.9%. CCA alone goes from 1,533 to 2,972 activities (79.7% → 89.5%). jungle becomes eligible, so BHD has 6 eligible projects instead of 5. Another 1,126 running activities have not yet passed their planned duration and stay without a label.
- What it means for the results: each added label is certain. But only overruns are added. The running activities that will finish within plan cannot be labelled, so the running part of a project enters the data as 100% overruns. A model can recognise that part through the planned position of an activity. The within-project AUC of BHD projects, CCA above all, can therefore be higher than the model deserves.
- Sensitivity S2, fixed now: the same analysis without these activities. That is the population of E1–E2b, so S2 is the result that can be compared with the earlier experiments; the main result cannot.
- Under S1 a running activity counts only if the time already elapsed passes the tolerance threshold. In the C-index running activities are left out, because only a lower bound of their ratio is known.
- DSLIB has no such activities (completed projects).

### 6. Flagged projects: kept, listed in code, with sensitivity analyses

- Decision: three projects stay in the corpus and are listed in `buildings.FLAGGED_PROJECTS` with the reason for each, so results can be reported with and without them.
  - DSLIB C2023-04: 29 of 30 activities are exactly 20% longer than planned (E2c). It is on the DSLIB list of projects whose tracking was corrected.
  - BHD Medor (`Update 01-09-2010`): planned durations taken from a plan revised after work started (E2b, section 8).
  - BHD rehab-2: planned start equals actual start in 100% of activities; 42% of the BHD rows of E2b.
- Sensitivity S3, fixed now: E3 is trained once more without C2023-04. The result with the project is the primary one. If the two are close, the document says the project does not matter; if not, the difference is reported as a limitation.
- Sensitivity S4, fixed now: the BHD development results are also reported without rehab-2.
- Alternative considered for C2023-04: drop it by a new rule. Rejected, because the rule would be written after seeing the project.

### 7. Risk bands: by rank inside the project

- Decision: the bands shown to the user (low / medium / high) are set by the rank of an activity inside its project, not by a fixed probability. Reason: the probability level differs a lot between corpora (E1), so a fixed threshold marks almost everything in one project and almost nothing in another.
- The cut-offs are fixed in the E3 plan entry, before E3 results, and are never tuned on the frozen set.

### 8. If the new model does not pass the quality gate: open

Not decided. It will be decided with the advisor after E3 and before the frozen evaluation. The frozen set is not touched until this is settled.

### 9. The freeze

- Decision: whole DSLIB families are drawn in seeded random order until the set holds ≥ 15 projects. The draw is accepted if it holds ≥ 6 projects eligible under decision 4; otherwise the next seed is tried, and every rejected attempt is recorded. BHD is not frozen: it has 7 projects and all are needed for development. The 13 DSLIB projects of E2c are dropped before the draw.
- Code: `src/freeze_test_set.py` makes the draw once and never rewrites it. `src/frozen.py` gives `development_only()` and `assert_no_frozen()`; every later script that trains, tunes, calibrates, sets thresholds or compares variants must use them.
- What it means for the results: see the list written into `outputs/frozen_test_set.json`. In short: the final number rests on about 6 projects, all from DSLIB; the frozen families were already seen in E1–E2c; the draw is conditioned on eligibility.

### Order of work from here

This entry → the draw → the E3 plan entry (variants, tuning grid, band cut-offs) → E3 → E4 → meeting with the advisor → one evaluation on the frozen set.

### Limits on validity that hold whatever E3 shows

- Few projects: 22 eligible in all, about 6 of them frozen. Confidence intervals will be wide.
- The final number describes DSLIB-like projects. For BHD-like projects there is no frozen evidence.
- BHD labels are measured against the plan as exported, which is not always the original plan (E2b, section 8).
- Decisions 1–7 were taken after E1–E2c had been seen. None was taken after an E3 result.

**What it shows.**
1. The position rule improves in all 5 projects that are eligible both ways, by 0.04 to 0.13 (median 0.08). The median over the eligible projects moves from 0.485 to 0.590. The rule learned nothing; the added activities sit later in the plan (in every project their median planned position is above that of the completed ones) and all of them are labelled as overruns.
2. `rel_position` is a model feature. A model could collect the same gain. A gain of about 0.1 is larger than every difference between a model and a baseline measured so far (E2b: at most 0.05).
3. The completed-only data are not free of bias either; theirs goes the other way. The rule is below 0.5 in three of the five projects (0.375, 0.415, 0.485): among completed activities, the later ones overran less. This is the survivorship effect of item 3 (E2b, section 9: in the late part only the fast activities had finished). The direction is not the same in every project, so it is harder for a model tested on a new project to use. Neither version is unbiased, and one snapshot per project cannot show where the truth lies.

**Decision (Roi and Shira, 15.11.2026).**
- Main analysis: completed activities only, as in E1–E2b.
- Sensitivity S2, redefined: the same analysis with the 1,731 running overruns labelled `grew` = 1. The numbers of decision 5 in D1 describe this sensitivity analysis.
- Reading rule, fixed now: if the model beats the best baseline only in the version with the running activities, the document says that the advantage probably comes from the link between planned position and the label, and reports it as a limitation.
- In the main analysis BHD has 5 eligible projects (jungle is eligible only in S2).

**Limits on validity.**
