## E1 — 8.11.2026 — Advisor items 1, 4, 5, 8: first checks

**Question.** Does scenario B's AUC 0.85 come from the model recognising projects (item 1)? Do duplicate project families inflate scenario A (item 4)? Does the model behave differently with the inputs the service really sends (item 5)? Does the model beat simple rules (item 8)?

**Run.** `python3 src/advisor_checks.py` → `outputs/advisor_checks.json` (about 1 minute).
- Corpus: `outputs/corpus_v3_buildings.csv` (registry v6 corpus, 66 projects, 9,250 activities).
- Model: XGBoost with the v6 hyper-parameters, fixed in every split (no nested grid search), so all variants are trained identically.
- Scenario A: 20 GroupShuffleSplits, 25% of projects in test. A_project groups by project (as in v6); A_family groups by schedule family.
- Families are generated by code from identical project signatures: 66 projects → 59 families. Merged: DSLIB C2016-18/19/20, C2016-21..24, C2016-25/26, and 129 trial with 130 TRIAL.
- Within-project AUC: projects with ≥30 test activities and ≥5 in each class (23 projects in A, 7 in B).

**Result (within-project AUC is the product metric).**

Paired within-project comparison, A_family (median of per-project differences, bootstrap CI over 23 projects):
- full − planned-duration rule: −0.002 [−0.051, +0.046] — **the v6 feature set does not beat the rule on a new project.**
- clean − planned-duration rule: +0.048 [+0.014, +0.095], better on 16 of 23 projects.
- clean − full: −0.016 [−0.037, +0.083], 10 of 23 — no demonstrated difference.
- as served − full: −0.000 [−0.006, +0.016].

Probability level when inputs arrive as served: DSLIB mean 0.174 → 0.155, BHD 0.482 → 0.497 (observed 0.174 / 0.483).

**What this shows.**
1. Item 1 confirmed. The two project features alone reach pooled AUC 0.816 in B and 0.740 in A, with zero ranking inside a project. On a new project (A_project), they score higher pooled than the full model (0.740 vs 0.734). Removing them drops B from 0.874 to 0.793 pooled, and from 0.769 to 0.650 within project. So in B the model also uses them to learn project-specific patterns.
2. Item 4 confirmed for the pooled metric. Grouping families drops the full model's pooled A from 0.734 to 0.640. Within-project AUC does not move (0.560 → 0.566), because the duplicate DSLIB projects are single-class and never enter the within-project metric.
3. Item 5: the train/serve mismatch barely changes ranking or the mean probability. It still has to be removed, because the evaluation must describe the model that runs.
4. Item 8: on a new project, the v6 model is not better than ranking by planned duration. The clean feature set is modestly better (+0.05 within-project AUC, top-10% lift 1.19).

**Caution (item 9).** These are exploratory comparisons on the same 66 projects that earlier decisions were made on. The clean set's advantage is a direction, not a final result. The final number must come from a frozen family-level test set, evaluated once.

**Decision.** Next model iteration: drop proj_span_days, proj_n_tasks, both float columns and task_type; group every split by family; headline = A_family within-project AUC with CI, next to the planned-duration rule. Before training it: clean the rows (item 6) and measure survivorship (item 3). No change to the served model yet.
